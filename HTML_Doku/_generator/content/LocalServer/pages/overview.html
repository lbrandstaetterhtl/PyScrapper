The HTTP layer of PyScrapper. It runs locally on 127.0.0.1:8765, keeps download jobs in memory, drives the engine and stores users, playlists and settings in a single SQLite file.

The state

One global ServerState object holds everything transient. It does not survive a restart — download jobs are deliberately not persisted.

FieldMeaning
jobstask_id → ServerJob, holding the contexts and the stream jobs
log_queueQueue capped at 5000 lines; one task drains it into the log file
download_limiterSemaphore, at most 10 downloads in parallel
search_limiterSemaphore, at most 10 searches in parallel
quit_eventSet by the /command endpoint
download_pathBase directory downloads are written to

cleanup_loop() runs in the background, checks every ten minutes and discards jobs older than 24 hours. That is the only cleanup that runs: cleanup_download(), meant to drop a single stream shortly after it was fetched, is defined but never called.

Authentication

There are three header-based schemes now, and most routes combine two of them.

HeaderDependencyChecks
X-Admin-Keyrequire_admin Constant-time compare against ADMIN_KEY from the .env. Guards the server as a whole.
X-User-Key + Authrequire_user Looks the user up by the identifier in Auth, compares the key with secrets.compare_digest, returns the user row
Authrequire_auth Only asserts the header exists; the endpoint decides whether it matches the record

On top of the dependencies there is a second, per-record layer. check_user_identifier() compares the identifier in the Auth header with the one on the record. owns_record() does the same for tables that carry a UserIdentifier column, and refuses any table not in the OWNED_TABLES allowlist — that allowlist is what keeps the table name out of the SQL string unchecked. owns_playlist() is a thin wrapper for the Playlists case.

Unknown identifier and wrong key deliberately produce the same 401, so valid identifiers cannot be enumerated through the error message. Both cases write a WARN line to the log queue.

The stored key is hashed, the comparison is not

/create/user/ (and /register, which calls it) stores hash_api_key(req.apikey), i.e. the SHA-256 hex digest. require_user then compares the incoming X-User-Key with compare_digest(request_api_key, row["ApiKey"]) — plaintext against digest. The earlier, unused request_api_key_hash line is gone entirely, so nothing in the dependency hashes the incoming key any more. As written, user authentication only succeeds if the client sends the hex digest itself. Hashing the incoming key with hash_api_key() before the comparison closes it.

One stream route has no key at all

The HLS routes (master.m3u8, the video and audio index.m3u8, the segments), the file watch route and /download/progress/... now declare Security(require_user). /stream/download/{task_id}/{stream_id} does not: its dependency was removed, so anyone who knows a valid task_id and stream_id can pull the finished file without a key. Both are UUID-based, and that is the only protection on that route.

The flip side of protecting the HLS routes: a plain <video> tag cannot set X-User-Key and Auth, so only players that add headers to every request (LibVLC, or hls.js with a custom loader) can play those streams.

The CORS configuration adds to this: allow_origins=["*"] together with allow_credentials=True. Browsers reject that combination anyway, and for a service on localhost a fixed origin list is the appropriate setting.

Platform specifics

On Windows the module sets asyncio.WindowsProactorEventLoopPolicy() before anything else is imported. The engine now drives ffmpeg and ffprobe as subprocesses fed through pipes (see core.processes.AsyncProcessManager in the engine documentation), and asyncio subprocesses only work on the Proactor loop there. The lifespan prints the active loop type on start, which is the quickest way to confirm it. pywin32 is in requirements.txt for the named pipes the process manager creates on Windows.
