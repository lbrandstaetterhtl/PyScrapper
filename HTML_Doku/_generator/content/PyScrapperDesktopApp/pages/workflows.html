PyScrapperDesktopApp / workflows

What happens when

The workflows that make up the day-to-day of the app, each in the order the code runs them.

Startup sequence

Program.Main first installs a handler for unhandled exceptions that writes CRASH.txt next to the exe. Then LibVLC is initialised — preferably from the bundled libvlc/win-x64 folder, otherwise from the system installation. Only then does Avalonia start.

App.OnFrameworkInitializationCompleted sets the shutdown mode to OnExplicitShutdown and queues the actual startup flow through Dispatcher.UIThread.Post. The comment in the code gives the reason: the flow must not run until the message loop is alive.

StepCodeResult
1AppConfig.Load()Server address and decrypted client key in AppData.Config
2LoginWindowWaits on a TaskCompletionSource for LoginResult
3Database.LoadSettingsFromApiAsync()Settings; on null a default set is created through CreateSettingsAsync
4RequestedThemeVariantLight or dark according to DarkModeEnabled
5LauncherWindowChecks the environment, returns a LauncherResult
6LoadApplicationData()Load media and playlists, then MainWindow

On LauncherResult.Cancelled the app exits with code 0, on Error with code 1. Once the main window is open the shutdown mode switches to OnMainWindowClose.

Note the ordering: login happens before the launcher, so the user key is already in AppData.CurrentUser by the time any per-user route is called.

Signing in

LoginWindowViewModel first checks with GetHealth() whether the server answers at all, then sends POST /login. On success the user lands in AppData.CurrentUser — with the API key immediately re-encrypted through SecretProtector.Encrypt(user.ApiKey) — the window sets LoginResult.Success and closes.

Register works the same way but calls Login directly after a successful registration, so the user does not have to sign in again.

Environment check in the launcher

OnWindowReady() runs these in order:

StepMethodChecks
1IsServerRunning()GET against port 8765; if that fails the flow ends with an error message
2EnsureVcRedist()Looks for VCRUNTIME140.dll in System32, otherwise downloads the installer and runs it with /install /quiet /norestart
3RestoreDotnetPackages()Finds every .csproj below the repository root and restores the packages
4EnsureFfmpeg()Makes ffmpeg available — needed for codec checks and conversion
5FinishSuccess()Status line to „Ready!“, result Success, window closes

Progress runs through the Messages collection of LauncherMessage entries (title, text, icon) that the window shows as a list. On an error ShowError() reveals an error panel with a close button.

Note on the XML documentation

The <summary> block above OnWindowReady also describes a Python installation, venv, pip, requirements, Playwright browsers and starting the server. What is implemented are the five steps in the table above; the remaining tasks belong to the server itself.

Loading data

LoadApplicationData() does more than load — it reconciles the stored data with the file system:

  1. Fetch media through GET /getuser/downloadedmedias/{id}.
  2. Check File.Exists(DownloadPath) for each entry. If the file is gone the entry goes on the removal list. Entries with the path "Does not exist" are on it from the start.
  3. For .mp4 additionally AudioPlayer.IsSupportedCodec(). Unsupported does not mean deleted but IsPlayable = false plus a WARN in the log.
  4. Register the remaining media through AppData.AddDownloadedMedia().
  5. Load playlists, call FindMedias() for each and register them.
  6. If ScanFolderOnStartup is set, scan the download folder.

At the end the method writes two summaries to the log: the number of listed and playable media including removed entries, and the number of playlists.

Search and download

Two windows share the job. ScrapWindowWithSearch for providers with a search, ScrapWindowWithoutSearch for the rest, where the URL is entered directly. Which provider goes where is decided by AppData.ValidSearchProviders.

PhaseCall
SearchPOST /search → List<SearchResultItem>
Start the downloadPOST /download/video-audio → DownloadResponse
ProgressGET {resource.ProgressUrl} every 500 ms
Fetch the fileGET {resource.DownloadUrl} as a stream
Register itPOST /create/downloadedmedia

Both windows always send download_strategy = "stream"; the server has the local strategy switched off. The search window also has an auto convert switch that is sent as auto_convert: the server then delivers the file already in the selected container, re-encoding through ffmpeg where needed. The direct-URL window does not send the flag.

The progress URL comes out of the response; it is not assembled by the client. ApiClient.GetFileFromStream() downloads with HttpCompletionOption.ResponseHeadersRead so large files do not go fully into memory, and takes a CancellationToken for cancelling. The file name now comes from the server's Content-Disposition header rather than from the extension the client guessed, and the method returns the final path.

Only after the file is on disk does the search window compare its extension with the selected type and ask whether to keep a mismatch. It then waits for the file with at most ten File.Exists checks (the loop used to be unbounded) and registers it through /create/downloadedmedia with the path and extension of the file that actually arrived.

Three rough edges in the new download path

The path is glued, not combined. GetFileFromStream() builds path + fileName. The search window passes the directory without a trailing separator (Paths[i] cut at the last \), the direct-URL window passes DownloadPath\Filename. The result is C:\DownloadsSong.mp3 or C:\Downloads\SongSong.mp3. Path.Combine(directory, fileName) with the directory in both callers fixes it.

The type check always fires. The search window compares finalPath.Substring(finalPath.LastIndexOf('.')) — which includes the dot — with SelectedMediaType.Trim('.'), which does not. The two never match, so the „Found only …“ question appears for every download.

„auto“ is rejected by the server. Choosing auto sends preferred_file = "" and preferred_type = "". The server's DownloadRequest validates any value that is not null with validateStr, which refuses empty strings, so the request fails with 422. Sending null instead of an empty string would let the server choose.

Progress display

ProgressBarWindowViewModel starts a background task that polls GetDownloadProgress() and reports percentage, status and speed to the surface. It ends through a CancellationTokenSource — either because the download finished or because the window was closed.

Filtering

MediaFilter holds the search text, media types, start and end date and a playability flag. On apply the app backs up the unfiltered state in OriginalDownloadedMedias and sets FilterEnabled. Reset restores from that backup — the filtered view is a replacement of the collection, not a separate view over it.

Playback

AudioPlayer wraps LibVLC and is IDisposable. It manages its own queue and offers PlayNext and PlayPrevious; IsSupportedCodec() checks a file with ffprobe before it counts as playable.

MediaPlayerControlViewModel binds that to the surface: stop, next, previous, volume, and MoveForward / MoveBackward, which shift the playback position by ten seconds each. ToggleCompact() switches between the compact bar and the full view. The control is IDisposable as well, so the LibVLC resources are released cleanly.

Converting

MediaConverter is the model behind the converter window and it is more than an ffmpeg call. Three tables drive it:

TableMeaning
ContainerCodecsWhich audio codecs a target container accepts, e.g. .mp4 takes aac, alac, mp3, ac3, eac3, flac, opus, vorbis, dts
ContainerVideoCodecsThe same for video: only .mp4, .mkv and .ts carry video at all
ContainerEncodersThe encoder plus quality settings per container, e.g. .mp3 → libmp3lame -q:a 2

For each stream the converter decides between three outcomes: the codec already fits the target container and is copied (copy, no re-encode), it does not fit and gets the container's encoder, or the target container is unknown and the conversion is refused. Video that has to be re-encoded goes through the fixed libx264 -crf 23 -preset fast -pix_fmt yuv420p.

MediaConverter.Convert(path, targetContainer) is static and returns the path of the result. MediaConverterWindowViewModel drives it: OpenFilePicker selects the input through StorageService and AppData.FileTypes, Convert runs the conversion, Cancel aborts it. The target container is picked from AppData.ValidMediaTypes and defaults to .mp4.

This converter works on files that are already on disk. Conversion during the download is a separate mechanism on the server side (auto_convert, see above).

Saving on exit

While loading, the app hooks desktop.Exit += OnExit. OnExit runs PerformExit() synchronously and sets the exit code to 0 or 1. PerformExit() builds a single SaveDataRequest out of the user identifier, playlists, media, assignments and settings, and sends it to POST /save. So the whole state goes back in one request rather than piecemeal during the session.
