PythonModule / architecture

From link to byte stream

The path of a request in five stages. Each stage has exactly one job and hands a clearly defined object to the next.

1 — Resolve the provider

The provider string from the request is turned into a ProviderTypes enum value through SUPPORTEDPROVIDERS. Every provider has several accepted spellings (youtube, youtube.com, www.youtube.com). Two mappings connect the enum to the functions: PROVIDER_SEARCH_MAPPING for search and PROVIDER_GETRESULTS_MAPPING for resolution.

Not every provider can do both. Default and wcoflix appear only in the getresults mapping, so they can be resolved but not searched. ProviderTypes also declares Aniworld, Dailymotion and ERROR, which have no entry in either mapping — the enum value exists, but resolving it fails.

YoutubeMusic is its own provider

ProviderTypes.YoutubeMusic maps to Youtube.searchMusic and Youtube.getMediaInformationMusic, and its aliases are music.youtube.com, youtubemusic and musicyoutube. It shares the Youtube package but takes a completely different route through it: a browser that harvests the streaming URL, rather than the player API calls the plain Youtube provider makes.

Filmpalast is registered but not finished

ProviderTypes.Filmpalast is in both mappings and has aliases (filmpalast, filmpalast.one, www.filmpalast.one). Its search() works on the HTML of the search page, but getMediaInformation() stops after opening a visible browser on every decoded host and returns None instead of a ProviderResult. A download request for it fails in the server when the context is built.

2 — Find the media

Every provider module implements getMediaInformation(request, ...). How it gets to the real URLs is up to the module. There are three patterns in the project:

PatternWhoHow
HTML regexBandcamp, Newgrounds, Suno, wcoflix Load the page, search for embedded stream URLs with a regex
Browser sniffingSoundcloud, YoutubeMusic, Default, Filmpalast Playwright starts Chromium, plays the media and records every media response
APIYoutube, Archive The YouTube player API (youtubei/v1/player) or the Archive API returns the format list

All of them end at the same point: a list of FoundMedia candidates that goes into makeProviderResult(). A candidate can now carry an audio_url next to its url when video and audio are separate streams.

YouTube without yt-dlp

Youtube.getMediaInformation() no longer asks yt-dlp. It posts the video id to the player API, trying the client identities in GET_METHODS in turn (visionOS, Android VR, Safari web). A LOGIN_REQUIRED answer is retried once with the visitorData from the response, then the next client is tried. From the first usable answer it takes, in this order:

  1. separate video and audio formats, scored by resolution, fps, bitrate and codec (VIDEO_CODEC_FACTOR / AUDIO_CODEC_FACTOR), with +1000 for the requested container — delivered as FILE with an audio_url;
  2. the hlsManifestUrl — delivered as HLS;
  3. a progressive format that already contains audio — delivered as FILE.

The request headers of the client that succeeded travel on as extra_headers, because googlevideo checks the user agent when the segments are fetched later.

The fallbacks are unreachable

_extractSeperatedVideoAudioFromFormats() guards with if not bestVideoCandidate, but BestCandidate is a dataclass instance and always truthy. The function therefore always returns a result, even when no format had a URL, and the HLS and progressive branches after it never run. An empty video_url then fails later in the scorer. Checking bestVideoCandidate.url instead fixes it.

Side effects on every call

_tryGetUsableUrls() writes the full format list to youtube_formats.txt in the working directory on each request, and _sendRequest() adds X-Goog-Visitor-Id to the module-level header dictionary itself, so the visitor id of one request sticks to every later request made with that client identity.

3 — Pick the best URL

makeProviderResult(found_media_list, request) is the single entry point. Candidates that arrive without an extension are completed by _makeFoundMediaFromUrl(), which derives extension, media kind, MIME type and download type from the URL and computes a base score. Then the client's wishes are added and the highest total wins.

SourceExamplePoints
MEDIA_EXTENSION_PRIORITYmp4 / mkv / webm / m3u8100 / 95 / 90 / 20
GOOD_URL_KEYWORDSmaster / playlist / index+100 / +80 / +70
BAD_URL_KEYWORDSpreview / thumbnail / ads−100 / −500 / −1000
Wish from the requestpreferred_type / preferred_file+200 / +1000

The base score is only computed for candidates that arrive without an extension. A candidate that arrives complete — the YouTube provider sends exactly one — keeps its prio of −1 and only gains points from the wishes. Since the winner has to beat the initial −1, such a candidate is rejected when neither preferred_file nor preferred_type matches it. The winner then goes through _buildProviderResultFromFoundMedia(), where getUrlInformation() asks the server for the size of the video URL and, if present, of the audio URL. The sum becomes the total size; for HLS it is set to −1, because progress is counted in segments there.

MEDIA_PRIORITY_FOR_QUALITY_AUDIO is still defined but no longer read anywhere, and makeProviderResultFromCandidate() is kept but unused.

The table mixes two levels

Extensions like m3u8 and mpd describe the transfer mechanism, while mp3 and mp4 describe the target format. Both sit in the same priority table. If the client sets preferred_file="mp3", a progressive MP3 URL wins with +1000 points against any HLS playlist.

4 — Build the context

The ProviderResult becomes one DownloadContext per file (the server does this in _resolveMediaAndCreateContexts). It bundles sub-objects that are read and written separately further down:

  • target — original URL, resolved URL, type, extra headers, POST body, and now audio_url, video_size and audio_size for separate streams
  • info — what was asked for (preferred_file, preferred_type) and what was found (found_file)
  • output — bare file name, file name with extension, destination path and auto_convert
  • download_progress — the progress the downloaders keep updating

Several contexts plus a session and a semaphore make up a DownloadInformation. That is the unit a dispatcher receives.

5 — Download

The DownloadDispatcher sorts the contexts by target.download_type into three buckets and starts one specialised dispatcher per bucket. For a single context there is now downloadContextAndYield(), which picks the matching dispatcher through _getManualDispatcher() — that is what the server's download route uses. All three inherit from the abstract Dispatcher and must supply exactly two methods:

MethodContract
_runContextLocal(context)Coroutine, writes the file to disk
_runContextStream(context)Async generator, yields byte chunks

From those the base class builds downloadToFile() (all contexts in parallel through asyncio.gather) and downloadAndYield() (all contexts one after another into a single stream). A context with no known type is silently set to FAILED in _splitContext() and dropped — it appears in no exception, only in download_progress.error_message.

Every stream goes through the codec check

All three _runContextStream() implementations hand their byte sources to _asyncProcessSources(video_source, context, audio_source):

  1. The first chunks of the video source are fed into AsyncFFmpegProbeCodec (ffprobe on a pipe) until it reports the codecs. The bytes read so far are buffered. The same happens for the audio source if there is one.
  2. The target container is info.preferred_file when auto_convert is set, otherwise the found extension.
  3. If there is no separate audio, the target is the found container and canMuxCodecsIntoContainer() agrees, the buffer and the rest of the source are yielded untouched.
  4. Otherwise an AsyncFFmpegMuxer is started with one input pipe per source. Codecs the container accepts are copied, the rest are re-encoded with the container's default encoder (see CONTAINERS). Two tasks feed the pipes while ffmpeg's stdout is yielded as the result.

So ffmpeg and ffprobe are no longer optional: every streamed download starts both.

Conventions in the code

Anyone extending this should know the house rules, because they are applied everywhere:

  • Check, do not trust. Almost every public function starts with Validate.* calls. Each gets a caller="[CORE] Class.method" that ends up in the error text.
  • Errors carry context. TaskFailedError takes task, reason and a list of extraMessages, used to pass on what to do about it. DRMProtectedMediaError is the newer, more specific case for encrypted streams.
  • Cycles are broken locally. The dispatcher imports its sub-dispatchers inside the methods, not at module level.
  • Naming is mixed. Functions are camelCase, parameters snake_case, attributes vary. Check the signature before calling.
