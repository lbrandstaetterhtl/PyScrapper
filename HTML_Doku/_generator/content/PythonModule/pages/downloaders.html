PythonModule / downloaders

The three download mechanisms

FILE, HLS and UMP. Which one is used depends solely on context.target.download_type — not on the file extension and not on the provider. Whatever the mechanism, a streamed download ends in the same codec check and, where needed, in ffmpeg.

FILE

One URL — or, since the YouTube rewrite, a video URL plus a separate audio URL. FileDispatcher builds one byte source per URL with asyncDownloadYieldRanges(), which walks the file in 10 MiB Range requests up to the size the provider measured (video_size / audio_size). Both sources go into _asyncProcessSources(); with a separate audio track that always means ffmpeg joins them.

core.network.file still holds the older variants of the same idea — with and without progress, sync and async, file and generator. The local path uses downloadToFile(), the HLS segment proxy in the server asyncDownloadYieldSimple() with a byte range.

No size, no bytes

asyncDownloadYieldRanges() loops while start < total_size. When getUrlInformation() could not read a size from Content-Range or Content-Length, the size is −1 and the stream ends immediately without an error: the client receives an empty file.

HLS

Two stages. The dispatcher first fetches the m3u8 as text and lets dertermineFileType() decide from the tags whether it is a master or an index playlist (anything that does not start with #EXTM3U is UNKNOWN_FILE).

StageClassJob
MasterMasterHLSDownload(master_url, session, extra_headers, preferred_languages) Pick the best video variant by bandwidth, find the matching audio rendition by language; getUrls() returns both URLs
IndexIndexHLSDownload(index_url, session, extra_headers) Build the segment list, stream the segments

Both classes now take plain URLs instead of a whole context. In the stream path the dispatcher creates one IndexHLSDownload for video and, if the master named one, a second for audio; total_segments is the sum of both lists. The two generators go into _asyncProcessSources(), so separate audio is joined by ffmpeg rather than by concatenating files as before.

The parsing lives in finder.py as free functions, with the regexes in PATTERN_MAPPING. An #EXT-X-MAP init section is stored as a segment with duration 0, and HLSSegment carries start_byte / end_byte for playlists that address ranges inside one file. Both matter for YouTube's fMP4 manifests and for the server's HLS proxy.

The local HLS path is out of date

HLSDispatcher._runContextLocal() still constructs MasterHLSDownload(context, ...) and IndexHLSDownload(context, ..., audio_url=...) and calls downloadToFile() without arguments — the signatures before the rework. Any LOCAL HLS download would fail with a TypeError or a validation error. The server currently refuses LOCAL downloads altogether, which is why this does not show.

The text fetch is the fragile step

Both entry points fetch the playlist with html.getHtml() and decode it as text. If resolved_url in fact points at a media file rather than a playlist, there is no clean error — you get a decode error from deep inside.

UMP

Google's own container format behind googlevideo.com. download.py is the only place where parsing happens at the byte level. getUMPMode() picks one of three transports from the resolved URL:

sabr_patcher.py isolates the request patching. Unlike FILE and HLS, UMP is stateful: the server only answers a POST body that contains the last received position. That is why DownloadTarget carries the post_body field — it exists solely for this path.

The SABR stream path yields nothing

In UMPDispatcher._runContextStream() the sabr branch assigns generator = download.downloadAndYieldSABRSimple(...) but never iterates it. The context is then marked FINISHED with zero bytes sent. Only the youtube and ump branches actually stream. The local path has a related slip: context.download_progress.speed = TaskStatus.FINISHED instead of status.

With the YouTube provider now resolving direct format URLs and HLS manifests itself, UMP is only reached by providers that still hand over googlevideo or watch URLs.

Probing and muxing

The core.ffmpeg package is what turns raw sources into a file the client can use.

PieceJob
AsyncFFmpegProbeCodec Runs ffprobe on a file or on a pipe and returns FFmpegCodec entries (name, type, input index)
canMuxCodecsIntoContainer Checks every codec against the container's allowed_codecs
CONTAINERS Per extension: ffmpeg format, allowed codec types, codecs that may be copied, default encoders and extra copy arguments
AsyncFFmpegMuxer ffmpeg with N input pipes and the output on stdout. writePipe() / closePipe() per input, output() yields the result and raises TaskFailedError with the last 30 stderr lines on a non-zero exit
FFmpegDownload Lets ffmpeg fetch URLs itself; exported but not used by any dispatcher

Underneath sits AsyncProcessManager. It creates the input pipes before the process starts — os.pipe() passed as pipe:<fd> on POSIX, a named pipe \\.\pipe\pyscrapper_input_<uuid>_<n> through pywin32 on Windows — and drains stdout and stderr according to a ProcessDrainType (manual, print, callback, none). A broken pipe while feeding the prober simply ends probing: ffprobe has seen enough.

ffmpeg and ffprobe are looked up with shutil.which(); if either is missing the constructors raise FFmpegNotFoundError.

Progress

All three mechanisms write into the same DownloadProgress on the context. updateDownloadProgress() derives speed and remaining time. The server simply reads that object when the client polls; there is no second state next to it. Note that the bytes counted are the bytes fetched from the source, not the bytes ffmpeg writes out — after a re-encode the two differ.
