🗺️ Systemüberblick

PyScrapper besteht aus zwei getrennt laufenden Prozessen auf derselben Maschine: dem C#/Avalonia-Desktop-Client und einem Python/FastAPI-Backend. Der Client ist ein reiner API-Konsument — er besitzt keine eigene Mediendatenbank mehr. Die gesamte Persistenz (Nutzer, Medien, Playlists, Settings) liegt beim Backend, das eine SQLite-Datenbank verwaltet. Lokal auf dem Client verbleiben nur zwei Dinge: die config.json (mit verschlüsseltem API-Key) und die Log-Datei.

🧱 MVVM-Schichten

Die App folgt strikt dem Model-View-ViewModel-Muster. Verdrahtet wird das über das CommunityToolkit.Mvvm, dessen Source-Generatoren aus Attributen automatisch Properties und Commands erzeugen — sichtbar an [ObservableProperty] und [RelayCommand] im Code.

SchichtOrtVerantwortungBeispiele
ViewViews/XAML-Darstellung, Bindings, Event-Handler im Code-Behind. Keine Geschäftslogik.MainWindow, LoginWindow, FilterWindow

📦 Kern-Datenmodelle

Alle Kernmodelle sind in Models/AppData.cs definiert. Sie bilden die Entitäten des Backends im Client ab. Beachte die Beziehungen: ein User besitzt Medien, Playlists und Settings; eine Playlist verknüpft über PlaylistMedia (mit Position) auf die Medien — eine klassische n:m-Beziehung mit Zwischentabelle.

Detail: DownloadedMedia

Das zentrale Medienobjekt. Es trägt die Metadaten eines heruntergeladenen Titels und den lokalen Dateipfad. Da es von ObservableObject erbt und seine Felder mit [ObservableProperty] markiert sind, propagieren Änderungen (z. B. IsPlayable) direkt in die UI.

Die statische Methode TryValidateFileName() prüft Dateinamen defensiv gegen leere Werte, ungültige Zeichen, End-Leerzeichen/Punkte und reservierte Windows-Namen (CON, PRN, COM1–9, LPT1–9 …). Genutzt wird sie beim Anlegen von Downloads.

Detail: Playlist & PlaylistMedia

Eine Playlist hält keine Medien direkt, sondern eine Liste von MediaIdentifiers. Die eigentliche Zuordnung inklusive Reihenfolge liegt in PlaylistMedia-Einträgen (Zwischentabelle). Die Methode FindMedias() füllt MediaIdentifiers aus den global gehaltenen AppData.PlaylistMedias, AddNewMedia() legt bei Bedarf einen neuen Zuordnungseintrag über die API an.

Detail: MediaFilter

Der Filter arbeitet nicht-destruktiv und rein clientseitig. ApplyMediaFilter() sichert die Originalliste, leert die sichtbare Collection und fügt nur passende Einträge wieder ein; ClearFilter() stellt den Originalzustand wieder her. Die Kriterien werden mit UND verknüpft (Titel-Teilstring, Medientyp, Datumsbereich, Spielbarkeit). Details dazu in den Workflows.

Synchronisierte Mutation

Damit die beiden Collections nie auseinanderlaufen, werden Medien ausschließlich über AddDownloadedMedia() und RemoveDownloadedMedia() verändert — sie pflegen DownloadedMedias und (bei IsPlayable) PlayableMedias gemeinsam.

public static void AddDownloadedMedia(DownloadedMedia media) { DownloadedMedias.Add(media); if (media.IsPlayable) PlayableMedias.Add(media); }

🔐 Konfiguration & Sicherheit

AppConfig (in Models/AppConfig.cs) lädt und speichert data/config.json. Der API-Key wird nie im Klartext auf Platte geschrieben: Save() verschlüsselt ihn über SecretProtector, Load() entschlüsselt ihn wieder. Im Speicher liegt zur Laufzeit der Klartext.

Verschlüsselung mit SecretProtector (DPAPI)

SecretProtector nutzt die Windows Data Protection API über ProtectedData.Protect / Unprotect mit DataProtectionScope.CurrentUser und einem festen Entropy-Wert. Der Schlüssel ist an das Windows-Benutzerkonto gebunden — es muss also nichts selbst verwaltet werden.

Grenzen: DPAPI schützt den Key auf der Platte, nicht im Speicher des laufenden Prozesses. Und wegen CurrentUser ist die config.json nicht portabel — sie lässt sich nur vom selben Windows-Nutzer auf demselben Rechner entschlüsseln. Auf einem anderen Rechner liefert Decrypt() einen leeren Key.

🌐 API-Kommunikation

Zwei Klassen sprechen mit dem Backend. ApiClient deckt die „Aktionen" ab (Download, Suche, Health, Login/Register, Progress). Database deckt die „Daten" ab (Laden/Anlegen/Löschen von Medien, Playlists, Settings sowie das gebündelte Speichern). Alle URLs werden einheitlich aus Config.ServerUrl + ":" + Config.ServerPort gebaut.

🔀 DTOs & Serialisierung

Request- und Response-Objekte liegen in Models/ServerRequestData.cs und Models/ServerResponses.cs. Jedes Feld trägt ein [JsonPropertyName(...)]-Attribut, damit die C#-PascalCase-Namen auf die snake_case-Felder des FastAPI-Backends abgebildet werden.

Download_path { get; set; } }

📝 Logging

AppLogger ist als Singleton mit einer Hintergrund-Queue implementiert (AppLogger.Instance). Aufrufer legen Meldungen nur in die Queue — ein einziger Consumer-Thread schreibt sie in logs/app.log. Das verhindert das „file is being used by another process"-Problem, das bei parallelem Direktschreiben aus mehreren Threads entsteht.

  • Jede Meldung ist ein Message(text, timestamp, type) mit Typ INFO / WARN / ERROR.
  • Der Aufruf kehrt sofort zurück (fire-and-forget) — Disk-I/O blockiert nicht die UI.
  • Beim Beenden sollte die Queue geflusht werden, damit die letzten Zeilen nicht verloren gehen.

📁 Pfad-Auflösung

AppData leitet mehrere Pfade relativ zum Arbeitsverzeichnis ab, indem es über Directory.GetParent(...) mehrere Ebenen nach oben geht bis zum Repo-Root.

PfadBedeutung
PyScrapperPathRepo-Root (enthält Client- und Server-Ordner)
AppLogsPathPyScrapperDesktopApp/logs
ServerLogsPathLocalServer/logs
DataPathPyScrapperDesktopApp/data (enthält config.json)
AssetPathPyScrapperDesktopApp/Assets
Achtung: Diese Auflösung setzt eine feste Ordnerstruktur voraus — PyScrapperDesktopApp und LocalServer müssen nebeneinander im Repo-Root liegen und die App aus dem erwarteten Arbeitsverzeichnis laufen. Bei abweichendem Deployment brechen die Pfade.
