🧰 Setup & Build

Voraussetzungen

  • .NET 9 SDK — die App zielt auf net9.0 (WinExe).
  • Windows für die volle Funktionalität — DPAPI (API-Key-Verschlüsselung) und der Launcher-Bootstrap sind Windows-orientiert. Avalonia selbst ist plattformübergreifend.
  • Eine IDE mit Avalonia-Support (Rider empfohlen; VS/VS Code gehen auch).
  • Das LocalServer-Backend muss im Repo-Root neben dem Client liegen — der Launcher prüft die Laufzeitumgebung und die Server-Erreichbarkeit.
Ordnerstruktur ist Pflicht: PyScrapperDesktopApp und LocalServer müssen nebeneinander im Repo-Root liegen. AppData leitet alle Pfade relativ dazu ab (siehe Architektur → Pfad-Auflösung). Läuft die App aus einem anderen Verzeichnis, brechen die Pfade.

Build & Start

# Restore & Build dotnet restore dotnet build # Starten (Debug) dotnet run --project PyScrapperDesktopApp # Release-Build dotnet build -c Release

Nach jedem Build läuft das Target GenerateVlcCache (in der .csproj) und erzeugt den LibVLC-Plugin-Cache. In Release wird das Avalonia.Diagnostics-Paket automatisch entfernt.

📐 Konventionen

MVVM mit dem CommunityToolkit

Properties und Commands werden nicht von Hand geschrieben, sondern per Source-Generator erzeugt. Das spart Boilerplate, hat aber eine Namenskonvention: aus einem privaten Feld mit Unterstrich-Präfix wird eine öffentliche Property in PascalCase.

// Feld _searchQuery -> generierte Property SearchQuery [ObservableProperty] private string _searchQuery; // Methode wird zu SearchCommand (bindbar im XAML) [RelayCommand] private async Task Search() { ... }
RegelKonvention
ViewModel-Feld_camelCase mit [ObservableProperty] → Property PascalCase
CommandMethode Xyz() mit [RelayCommand] → XyzCommand im XAML
Ein VM pro FensterFooWindow.axaml ↔ FooWindowViewModel.cs
Design-Mode-GuardViewModels prüfen Design.IsDesignMode, um Laufzeit-Code im Designer zu vermeiden
DTO-MappingJedes Request/Response-Feld trägt [JsonPropertyName] (snake_case)
Compiled Bindingsx:DataType in Views gesetzt (AvaloniaUseCompiledBindingsByDefault)

Styling zentral im Design.axaml

Farben, Verläufe und Control-Themes liegen gebündelt in Design/Design.axaml. Wiederkehrende Klassen wie UILabel, UIValue, UIHeader, Cell, CellInteractive, SeparatorHorizontal, SplitterVertical und primary (Buttons) werden über Classes="..." zugewiesen. Neue UI sollte diese Klassen wiederverwenden statt eigener Inline-Styles.

Theme: Hell/Dunkel wird über App.ToggleTheme() gesetzt, das den RequestedThemeVariant ändert und in den Settings persistiert. Icons wechseln je nach Modus zwischen den Ordnern Assets/DarkMode und Assets/LightMode.

🧩 Service-Layer

Neben ApiClient und Database gibt es drei kleine Dienste, die die UI von Infrastruktur entkoppeln.

ServiceAufgabeMethoden
DialogServiceStandarddialoge relativ zu einem Owner-FensterShowAlertAsync, ConfirmAsync, AskInputAsync
StorageServiceDatei-/Ordner-Picker über Avalonias StorageProviderOpenFilePickerAsync, SaveFilePickerAsync, OpenFolderPickerAsync
AppLoggerThread-sicheres Logging (Singleton)LogNewMassage, LogDebugMessage
StorageService braucht ein TopLevel: Er wird aus TopLevel.GetTopLevel(window) erzeugt. Wird er angelegt, bevor das Fenster im Visual Tree hängt, ist TopLevel null und der Zugriff wirft eine InvalidOperationException. Also erst nach dem Öffnen des Fensters instanziieren.

🔌 Interfaces (Contracts)

In Models/Interfaces.cs sind die Verträge der Dienste gebündelt: IApiClient, IStorageService, IAppLogger, IAppDataService und IDialogService. Sie sind die Basis für Testbarkeit — gegen ein Interface lässt sich ein Mock einsetzen, gegen die statische AppData nicht.

In der Praxis wird AppData überwiegend statisch verwendet, während die Dienste (ApiClient, DialogService, StorageService) als Instanzen an die ViewModels übergeben werden. Die Interfaces beschreiben also den Vertrag, den ein ViewModel erwartet — welche Methoden es aufrufen kann, ohne die konkrete Implementierung kennen zu müssen.

📝 Logging im Detail

AppLogger ist ein Lazy-Singleton mit einer ConcurrentQueue und einem einzelnen Consumer-Thread. Aufrufer legen ihre Meldung in die Queue (per SemaphoreSlim signalisiert) und kehren sofort zurück — nur der eine Worker-Thread schreibt in die Datei. So kann es nie zu „file is being used by another process"-Fehlern kommen.

Verwendung

private static readonly AppLogger _logger = AppLogger.Instance; _logger.LogNewMassage(new Message("Etwas ist passiert", DateTime.Now, "INFO")); // Typen: INFO · WARN · ERROR. Format: yyyy-MM-dd HH:mm:ss [TYPE] Text
Robustheit: Bei einer IOException legt der Worker den Eintrag zurück in die Queue und versucht es nach kurzer Pause erneut — es geht also nichts verloren, wenn die Datei kurz gesperrt ist. Beim Shutdown flusht Dispose() die restliche Queue. Tipp: Dispose() beim Beenden aufrufen, damit die letzten Zeilen sicher geschrieben werden.
Debug-Variante: LogDebugMessage() macht dasselbe, schreibt die Zeile aber zusätzlich auf die Konsole — praktisch beim lokalen Entwickeln.

🎧 Audio & Codec-Handling

AudioPlayer kapselt LibVLCSharp und bietet neben Wiedergabe (inkl. Playlist-Modus und Shuffle) auch die Codec-Prüfung. Beim Abspielen einer .mp4 wird über IsSupportedCodec() geprüft, ob der Video-Codec unterstützt wird.

  • Wird ein nicht unterstützter Codec erkannt, fragt die App, ob nach H.264 konvertiert werden soll (öffnet den CodecConverterWindow).
  • LibVLC wird bewusst mit --avcodec-hw=none initialisiert (Hardware-Decoding aus), um Kompatibilitätsprobleme zu vermeiden.
  • Das IsPlayable-Flag eines Mediums spiegelt das Ergebnis dieser Prüfung wider und steuert, ob ein Eintrag in PlayableMedias landet.
Der Codec-Check ist auch der Grund, warum das Datenladen beim Start etwas dauern kann: jede vorhandene .mp4 wird einmal geprüft (siehe Workflows → Datenladen).

➕ Ein neues Fenster/Feature hinzufügen

  1. View anlegen: Views/FooWindow.axaml (+ Code-Behind). Styles aus Design.axaml per Classes nutzen, x:DataType setzen.
  2. ViewModel anlegen: ViewModels/FooWindowViewModel.cs, von ObservableObject ableiten, Properties/Commands per Attribut.
  3. Öffnen vom aufrufenden VM per [RelayCommand] — als Dialog (ShowDialog(owner)) oder Fenster (Show()).
  4. Braucht das Feature Serverdaten? Passenden Aufruf in ApiClient oder Database ergänzen, dazu ggf. neue DTOs mit [JsonPropertyName].
  5. Zustand über AppData.Add.../Remove... ändern, damit die UI-Bindings reagieren.
  6. Wichtige Schritte über den AppLogger loggen.
Faustregel: Views zeigen nur an, ViewModels entscheiden, Models/Services reden mit der Außenwelt. Kommt HTTP oder Dateizugriff ins ViewModel, gehört es wahrscheinlich in einen Service.

🔄 Datenfluss an einem echten Beispiel

Um zu verstehen, wie die Schichten zusammenspielen, hilft ein konkreter Ablauf. Beim Löschen eines Mediums über das Kontextmenü der Medien-Tabelle passiert Folgendes im Code-Behind des MainWindow:

private async void DeleteMedia(object sender, RoutedEventArgs e) { // 1. Das gemeinte Medium kommt aus dem DataContext des MenuItems if (sender is MenuItem { DataContext: DownloadedMedia media }) { // 2. Nutzer bestätigen lassen (DialogService) var result = await _ds.ConfirmAsync("...wirklich entfernen?"); if (!result) return; // 3. Lokalen Zustand ändern -> UI aktualisiert sich automatisch AppData.RemoveDownloadedMedia(media); // 4. Serverseitig löschen await Database.DeleteDownloadedMedia(media.Identifier); // 5. Vorgang protokollieren _logger.LogNewMassage(new Message("Media removed: " + media.Url, DateTime.Now, "INFO")); } }

Dieses Muster zieht sich durch die ganze App und ist der Schlüssel zum Verständnis:

Der wichtigste Mechanismus: Schritt 3 ändert nur eine ObservableCollection in AppData — die Tabelle im Fenster aktualisiert sich von selbst, weil sie an diese Collection gebunden ist. Niemand ruft „UI neu zeichnen" auf. Das ist der Kern von MVVM in diesem Projekt.

Wie View und ViewModel verbunden werden

Die Verbindung entsteht im Code-Behind (Konstruktor) der View über den DataContext. Dienste werden dabei hineingereicht:

// LoginWindow.axaml.cs DataContext = new LoginWindowViewModel(new DialogService(this), this); // MainWindow.axaml.cs _ds = new DialogService(this); _vm = new MainWindowViewModel(_ds); DataContext = _vm;

Im XAML greifen die Bindings dann auf die Properties und Commands des ViewModels zu. Einzelne Zeilen einer Liste haben ihren eigenen DataContext (das jeweilige DownloadedMedia bzw. Playlist), weshalb Event-Handler ihn per Pattern-Matching auslesen können — genau wie oben bei DeleteMedia.

🧭 Verhalten verstehen

Ein paar Eigenheiten des Programms sind nicht sofort offensichtlich, aber wichtig, um es richtig zu lesen und Fehler zu deuten. Sie sind Teil davon, wie die App funktioniert — nicht Bugs.

VerhaltenErklärung
Login ist Pflicht vor allem anderenErst nach erfolgreichem Login ist AppData.CurrentUser gesetzt. Der Startablauf ist so gebaut, dass die App ohne gültigen Login herunterfährt, bevor Datenladen oder Speichern überhaupt erreicht werden — auf CurrentUser wird also bewusst erst danach zugegriffen.
config.json ist an Rechner + Nutzer gebundenDer API-Key ist per DPAPI (Scope CurrentUser) verschlüsselt. Kopiert man die Datei auf einen anderen Rechner oder Nutzer, liefert die Entschlüsselung einen leeren Key. Die Datei ist absichtlich nicht portabel — das ist die Sicherheitseigenschaft.
Pfade sind relativ zum Repo-RootAppData löst alle Pfade über Directory.GetParent(...) auf. Deshalb müssen Client- und Server-Ordner nebeneinander liegen und die App aus dem erwarteten Verzeichnis laufen.
StorageService braucht ein sichtbares FensterEr wird aus dem TopLevel des Fensters erzeugt. Vor dem Attach ans Visual Tree ist dieses null — deshalb wird der Picker erst im geöffneten Fenster angelegt.
Start kann etwas dauernIst ScanFolderOnStartup aktiv, wird jede Datei im Download-Ordner per API angelegt und ihr Codec geprüft. Das ist gewollt gründlich — daher ist die Option standardmäßig aus und im Menü mit Hinweis versehen.
IsPlayable ist ein PrüfergebnisDas Flag wird beim Laden und nach Downloads über AudioPlayer.IsSupportedCodec() gesetzt. Es entscheidet, ob ein Medium in PlayableMedias landet — es ist keine manuelle Einstellung.
Speichern passiert gebündelt am EndeWährend der Sitzung wird der Zustand in AppData gehalten; erst beim Schließen schreibt OnExit alles in einem /save-Aufruf. Wer den Prozess hart abbricht, verliert die Änderungen seit dem letzten Speichern.
Beim Debuggen zuerst hier schauen: Startet die App nicht bis zum MainWindow, hilft ein Blick in logs/app.log (bzw. das LogsWindow) und in die Health-Ansicht — sie zeigen, ob Login, Launcher-Prüfung und Backend-Erreichbarkeit jeweils durchgelaufen sind.
